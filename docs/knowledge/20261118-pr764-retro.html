流程与工具 本可避免

  • main 红着还重跑同一个失败 job
  • 关 #749 时没等 main 转绿

PR 自己的代码 审计阶段已修

  • 过期识别结果覆盖剪贴板（两个窗口，两次修复）
  • 辅助进程缺编辑快捷键；非拉丁键盘布局回退

两位都只读，不改任何东西。Fable 能访问 GitHub；Codex 的沙箱连不上，只读了本地 git 和 handoff。原文见下，已按事实核对过的部分去掉了我 brief 里的两处错（PR 是 11-18 才开的，不是 11-16；冲突标记在备份 head 13b2810e，不是 34bbcc9e）。

各自排出的三项改进

Fable

  1. 修或串行化 #706/#711 测试并重开 #749；加规则“main 最近一次 CI 红时不启动 rebase 与验证循环”。一个只改测试的 PR，约 1–2 小时加一轮 CI。唯一解锁 #764 的事。
  2. PR 描述在 gh pr create/gh pr edit 前本地跑 lint，最好放进 push-guard。约 30 分钟。
  3. 已审计的 PR 最早的先合并，合并前才 rebase 一次；台账一律用行级解析器，rebase-verify.sh 加标记 grep。约一小时加一条顺序规则。合并队列更好但没有 merge_group 触发器，成本更高。

Codex

  1. 去掉依赖调度时序的测试协调，从 #749 后续开始，并在受控的执行器饥饿条件下验证。1–2 天。
  2. 串行化最终落地准备：队首 rebase 一次，验证结果 base/head，只在证明等价时沿用旧审计。2–4 天。
  3. 自动化最终预检：冲突标记、对当前 head 的 PR 描述 lint 与 checker 确认、带保留意见的结构化冒烟结论。1–2 天。

两边都没能核实

Fable：第 1 次 attempt 的失败日志（gh 返回了第 2 次的日志）；“步骤 6 被误判”只能确认报告里写的是 5/5 通过；没有 11-17 之后的 delegator 日志；没找到专门跟踪红 main 的 issue（现在 #749 已重新打开）。Codex：完整 CI run 列表、PR 时间线与评论、分支保护、当前合并状态、44270101311/44270101888 两次失败。
