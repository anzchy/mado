## 1. 摘要

- **发生了什么。** 从 11-05 起，App tests 在 CI 上时红时绿，几乎都是只在 CI 上出现、重跑能过的失败。外部审计统计 main 最近 100 次 push 里 14 次红，其中 13 次是 App tests。[V] PR 一次次手动重跑才能合并，#590 跑了 4 次；rc tag 要求 tag SHA 上 App tests 绿，于是被拖住。[V]
- **为什么一直没停。** 三件事合在一起，让失败没有代价：App tests 不是 required check，Walking skeleton 在 App 测试失败时仍然通过；遇到红就手动 `gh run rerun --failed`；「先复现再修」被理解成「先在本地复现」，而本地复现不出来。[V]
- **怎么打破的。** #597（issue454）改成在 CI 上用一个只做诊断的循环复现：单个测试 ×20 → 10 次失败，4 轮诊断后看清是一个时序竞争，#603 修好。[V] 然后把这套循环和失败时的窗口状态打印正式放进 main（#606 / PR #607）。[V]
- **学到的最重要一点。** 「重跑通过」不等于「不是 bug」。#597 是真实的产品竞争，只是 Mac mini 太快，几乎撞不上。[V]

## 3. 原因

两位评审在 R1–R3 上一致，R4 只有 Fable 查到日志证据。

| # | 原因 | 涉及 | 把握 |
|---|---|---|---|
| R1 | **异步结果落地时，读的是「现在」的共享状态，而不是操作开始时拿到的值。** `openFolder` 的 catch 用 `session.folderScan?.failure == nil` 决定要不要弹授权。用户（或测试）点 Retry 会先清掉 failure，旧 catch 之后才恢复执行，于是走进「没失败 → 弹授权」。代码里本来有「操作是否已过期」的检查，但它只挡得住「操作被替换」，挡不住「同一操作里状态被改写」 | #597（已修） | 高 [V] |
| R2 | **用固定时长等系统状态。** 子进程测试激活窗口后只跑 0.2 秒或最多 2 秒，就断言它已是 key window；runner 上激活更慢时就红 | #564、#598、#599 | 高 [V]（失败都停在这一行） |
| R3 | **写死 2 秒上限。** issue507 测试给授权到扫描整条链 2 秒，日志里扫描还没开始就到时了 | #600 | 中 [V] |
| R4 | **用 AppKit 副作用当断言。** `!window.isVisible`、`attachedSheet == nil` 测的是「有没有任何弹窗」，所以任何迟到的弹窗都会让它红。#606 还看到：整包跑到后面时，前面的测试留下了挂着「This File Can't Be Opened」「Folder Access Failed」弹窗的窗口 | #520（候选，同 R1 模式）、多数 App 测试 | 中高 [V]/[I] |
| R5 | **CI 机器慢只是放大器。** 它让 R1–R4 的时间窗变宽，但不是原因；换更快的机器反而会把问题藏起来，Mac mini 就是例子 | 全部 | [I] |

## 4. 我们自己的做法哪里在制造循环

| 做法 | 为什么有问题 | 改成 |
|---|---|---|
| 「先复现」= 先在本地复现 | 本地快，撞不上竞争；GUI 锁 + 串行让本地大量重复很贵 | 先在出问题的环境复现：CI 循环是第一步，本地只用来调试已经定位的点。Owner 规则「复现属实后再修复」不变，变的是在哪复现 |
| 红了就手动重跑再合并 | 等于没有上限、没有记录的重试，绕开了「只自动重试一次、签名精确匹配」的设计，失败率也测不出来 | 待 owner 决定（§7） |
| App tests 不拦合并 | 失败没有代价，直到发版被卡 | #587 第 2 步；门槛待定（§7） |
| 复现循环写在一次性分支上，用完就扔 | 下一个 flake 又从零开始 | 已改：#606 放进 main |
| 先猜原因再修 | — | 这次没有发生：#597 的 i597 各轮都是只加诊断的轮次，修复是在看到原因之后才做的。之前给两位评审的摘要把它们写成了「猜测性修复」，是我写错了，在这里更正 [V] |

## 5. #606 自己踩到的坑（同样值得记住）

| 坑 | 怎么发现的 | 教训 |
|---|---|---|
| 四个测试目标各有一份等待函数，有测试要求它们一字不差；只改了 AppTests 那份 | CI 上 Package tests 失败（`i392ConditionWaitCopiesStayIdentical`） | 共享代码的「副本必须一致」守卫是真规则；差异放到核心之外的小文件里 |
| 失败时的处理放在主线程上，非主线程的等待被取消时要先等主线程空出来 | 本地全套检查：取消用了 71 秒（上限 30 秒）；CI 上同一版本通过 | 诊断代码绝不能让失败路径阻塞或切线程；本地全套检查和 CI 能发现不同的问题，两边都要跑 |
| 窗口最多列 20 个，整包跑时被前面测试留下的窗口占满，新测试自己的窗口被截掉 | 本地整包跑 306 个里 1 个失败，单独跑能过 | 测试要在「环境里已经有很多东西」时也成立；诊断输出新的在前 |
| 运行时给 AppKit 窗口换子类做探针 | 第 0 轮 CI 每次都崩 | 诊断只读状态，不改类、不 swizzle |
| 「先失败」记录的测试和被测代码写在同一个文件 | 最终验证判定无效 | 记录用的测试文件只放测试 |

## 6. 可复用的最佳实践

每条回答：做什么、在哪里、防住什么失败、资深开发者会怎么说。

| 做法 | 在哪里 | 防住什么 | 一句话 |
|---|---|---|---|
| **在失败的环境复现。** 单个测试 ×20、全量 ×5，不重试、空隔离，每次单独留日志 | `docs/agents/ci-flake-repro.md`；`gh workflow run ci.yml -f app_filter=… -f app_repeat=20` | 本地「复现不出」就放弃，或凭猜测修 | "Reproduce where it fails, not where it's convenient." |
| **失败时自动打印现场。** 窗口、key/main、弹窗文字，去掉路径，限长 | `AppTests/ConditionWaitState.swift` | 每个新 flake 都要先跑一轮诊断才知道发生了什么 | "Make the first failure carry enough to debug it." |
| **异步结果只用开始时捕获的值决策**；要读当前状态，先确认这个结果仍属于当前的那一次 | #603 的 `handleFolderOpenFailure`；审计维度 D3 | 迟到的结果按别人的状态做出错误决定（#597） | "Capture, don't re-read." |
| **用确定性的暂停点重放顺序写 RED**，而不是靠多跑几次碰运气 | #603 的 issue597 测试（挂起扫描、再点 Retry） | 修复无法被证明，回归无人发现 | "Make the race a test, not a statistic." |
| **等条件，不等时间。** 等通知或条件成立，上限交给测试自己的时间限制 | `waitUntil` / `runLoopUntil`；#564 等的修法 | 慢机器上的固定等待失败（R2、R3） | "Sleep is not synchronization." |
| **断言决策，不断言副作用。** 给弹窗之类的入口留可注入的接口，测试收集请求 | #603 的 `folderGrantPromptOverride` | 任何迟到的弹窗都让无关测试变红（R4） | "Test the decision, not the pixels." |
| **重试有上限、有记录。** 未知失败不重试；已知 flaky 只自动重试一次、签名精确匹配；隔离要有 owner、到期日、issue | `scripts/ci/known-flaky.mjs`、`scripts/tdd/app-quarantine.json` | 重试把真 bug 洗成「flake」 | "A retry is a measurement, not a fix." |
| **用测得的失败率做放行门槛。** 失败率约 13% 时，连续 5 次绿大约一半靠运气（0.87⁵ ≈ 0.50，Fable 计算） | #587 第 2 步（待定） | 「看起来稳定了」就提前设为必过 | "Count, don't vibe." |
| **不靠换快机器解决偶发失败** | — | 把竞争藏起来，换到用户的机器上出现 | "Faster hardware hides races; it doesn't fix them." |
