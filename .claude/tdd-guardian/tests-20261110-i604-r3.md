## Unit: CanvasWindowController sidebar presentation/load path (WI-2)

**Law**: Main-read failure owns the failed-child presentation even when an independent successful sidebar operation for the same navigation finishes later. Matching folder/generation alone cannot authorize restoring the successful-child projection after failure.

### Case: issue604SameOpenLateSidebarSuccessCannotReplaceFailureTree
- **Category**: state
- **Lane**: integration (headless App bundle `app-red`; no showWindow/orderFront or GUI interaction).
- **Spec level**: S5 — main failure → recovered root tree → same-open late sidebar listing/count preserves failure authority.
- **Input**: Real Parent/{Locked,Readable}, with distinct image counts. Open Parent, then Locked. Let Locked sidebar enumeration capture a successful real listing, but hold its return. While that listing remains held, release the main scanner with a read failure; Parent stays readable. Await the recovered failure tree. Release the held successful Locked listing and its following successful count for the very same open, with no folder switch or generation replacement caused by the test; explicitly await the old operation's completion.
- **Expected output**: Before release, Parent is L0, Locked uniquely selected at L1 with visible `—`, Readable actionable at L1. After same-open successful listing and count have returned and had their callback opportunity, exactly that topology, selection and failure dash remain. Parent/Readable counts retain their applicable values; no duplicate row and no successful-child-only tree can replace failure presentation.
- **Observable side effect**: Tree tuples, unique current row, count labels and read-failure page after confirmed boundary completion.
- **Assertion strategy**: Level 4 — assert exact URL/depth/current state before and after releasing the successful same-open listing; await explicit completion rather than asserting immediately after release. Level 1 — assert the failed child still shows visible `—` after its real numeric count returns. This kills an implementation relying only on stale-generation guards.
- **Mock boundary**: Gate the return timing of the real Locked filesystem listing and deterministic main scan failure. Delegate successful listing/count to production SystemSidebarFolderEnumerator. Do not fake a different generation or URL to make cancellation guards sufficient.
- **Paired integration test**: `issue604ReadableChildRetainsExistingProjection` and `sidebarListingCountsRealDirectImagesAndKeepsLease` cover production successful listing/count and complete App scan paths.
- **Refactor that would break this**: Allowing any generation-current onRows callback to restore normal projection despite the main-read failure; allowing the late successful count to replace `—`; protecting only cross-navigation stale results.
