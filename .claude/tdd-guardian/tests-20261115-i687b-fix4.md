# Test matrix

- WI-1: `issue687Fix4SuccessNoticeJoinsKeyboardAndAXFocusLoop` traverses the actual NSWindow key loop with Inspector shown and hidden, reverses from the successor, sends Tab through the viewer focus router, sets AX focus, and sends Space through the window. `issue687Fix4ReturnOpensFocusedNotice` sends Return.
- WI-2: `issue687Fix4WarningHasNoAXPress` checks the warning role, focusability, press selector and Tab exclusion. Error notices use the same warning kind.
- WI-3: `issue687Fix4PanelEditorAllowsAnnotateMenuAndShortcut` validates View menu and sends Command-E through the hosted responder chain; another NSTextField remains refused.

## Spec adversary

Direct `keyDown` calls would miss the device failure, so the first test uses `selectNextKeyView` and window event delivery. A direct `enterAnnotateMode()` call would bypass disabled menu validation, so the third test uses the real menu and shortcut. Existing #692 tests guard text input behavior after the exception.

The first warning assertion used AppKit's in-process `accessibilityActionNames()`, which was empty even though the signed device exposed AXPress. Before production edits, the test added a `responds(to: accessibilityPerformPress)` assertion and rerecorded the affected REDs. The command shortcut test uses the app menu's `performKeyEquivalent` because sending a synthetic command event only to `NSWindow` bypasses `NSApplication` menu dispatch.
