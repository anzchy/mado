# Test Matrix — WI-1: Split local Swift tests and preserve combined coverage

Plan: `.claude/tdd-guardian/plan-20261110-i632.md`

Use `node:test`, real temporary files and actual child processes. Executable fixtures stand in only for external Swift/LLVM/build tools. Avoid mocking repository modules. Store Node tests beside the scripts they exercise.

## Unit: Shared Swift unit runner

**Law**: Partition executions never overlap; a successful run requires both current partitions to complete successfully. A failed attempt cannot retain successful coverage evidence from an earlier attempt.

### Case: Split runner completes both partitions without concurrent MacUI
- **Category**: success
- **Lane**: integration
- **Spec level**: S5 — ordering invariant across the two partition transitions.
- **Input**: Swift executable fixture with one non-UI test and one MacUI test. The fixture rejects MacUI execution without `--no-parallel`; each partition holds a temporary exclusive marker until exit.
- **Expected output**: Exit 0; completed counts 1 and 1; total 2; neither overlap nor unsafe-MacUI failure.
- **Observable side effect**: Distinct current-run profile contents and completed evidence for both partitions.
- **Assertion strategy**: Level 1/2 — assert returned status, printed partition/total counts, exclusive-marker safety, and preserved profile contents. Check exact CI-equivalent partition arguments only as supplemental contract assertions.
- **Mock boundary**: External `swift` executable; fixture makes unsafe scheduling observably fail.
- **Paired integration test**: Real split package and LLVM coverage acceptance.
- **Refactor that would break this**: Changing public partition/count reporting or violating execution order; internal renaming should not.

### Case: Either partition failure invalidates the run without retry
- **Category**: failure
- **Lane**: integration
- **Spec level**: S5 — failure revokes the previous success state.
- **Input**: First establish a successful run and LCOV; then run fixtures where non-UI exits 1, or MacUI exits 1 after non-UI succeeds.
- **Expected output**: Each attempt exits nonzero, names the failed partition, publishes no successful total or usable coverage authorization.
- **Observable side effect**: Old successful evidence/report cannot be consumed; each partition is attempted at most once.
- **Assertion strategy**: Level 1/2 — assert status/output and that coverage export fails afterward; inspect fixture attempt records to prove no retry.
- **Mock boundary**: External `swift` executable.
- **Paired integration test**: Real split package and LLVM coverage acceptance.
- **Refactor that would break this**: Changing public failure policy or accepting stale success; implementation rearrangement should not.

### Case: Incomplete or empty successful-process output is not a completed suite
- **Category**: guard
- **Lane**: integration
- **Spec level**: S3 — catches false success from an incomplete runner.
- **Input**: Fixtures exit 0 with zero tests, with a started-but-unfinished test run, or with no test summary.
- **Expected output**: Nonzero runner status identifying invalid/incomplete test evidence.
- **Observable side effect**: No current-run coverage authorization.
- **Assertion strategy**: Level 1/2 — assert error and subsequent coverage rejection.
- **Mock boundary**: External `swift` executable.
- **Paired integration test**: Real split package and LLVM coverage acceptance.
- **Refactor that would break this**: Weakening the public success contract; parser internals may change.

### Case: Runner bounds a hung Swift process and reports timeout
- **Category**: failure
- **Lane**: integration
- **Spec level**: S3 — exact lock-retention failure mode.
- **Input**: Short test deadline; Swift fixture starts a TERM-resistant child in its own process group, records its PID, and hangs.
- **Expected output**: Exit 124; timeout diagnostic names the affected partition; no retry or successful total.
- **Observable side effect**: Recorded leader/helper PIDs are dead after bounded cleanup; diagnostics exist; coverage is invalidated.
- **Assertion strategy**: Level 3 — run actual processes, measure wall-clock upper bound with generous scheduling margin, test PID liveness, read diagnostics, and assert export rejection.
- **Mock boundary**: External Swift command only; use the real repository watchdog and OS process operations.
- **Paired integration test**: Existing `test-watchdog.test.mjs` cases “a hung helper in its own process group is killed when the leader exits on TERM” and “a helper orphaned by a leader that exited normally is found by the snapshots and killed.”
- **Refactor that would break this**: Changing timeout exit/diagnostic contract or losing worker termination; watchdog internal renaming should not.

### Case: Lock waiting does not consume the inside-lock test deadline
- **Category**: boundary
- **Lane**: integration
- **Spec level**: S5 — test budget starts after admission.
- **Input**: Hold an isolated test lock briefly, queue the actual launcher with a short Swift deadline, then release the holder; successful fixture runs shorter than the test deadline but later than that deadline measured from initial queueing.
- **Expected output**: Exit 0 after admission; no premature Swift timeout while waiting.
- **Observable side effect**: Fixture starts only after lock release; completed coverage evidence.
- **Assertion strategy**: Level 3 — assert actual admission timestamps, bounded completion, status and evidence. Use a unique lock path so this test does not contend with production work.
- **Mock boundary**: External Swift fixture; actual lock launcher.
- **Paired integration test**: Real split package and LLVM coverage acceptance, which uses the mandatory shared lock.
- **Refactor that would break this**: Moving deadline enforcement outside lock acquisition or changing admission semantics.

## Unit: Coverage export for split runs

**Law**: Current-run coverage conserves contributions from both partitions; exporting again is idempotent, and a new run replaces the previous run’s contributions.

### Case: Complementary profiles preserve both partitions’ coverage
- **Category**: success
- **Lane**: integration
- **Spec level**: S5 — conservation across capture, second execution and export.
- **Input**: Two instrumented fixture profiles for the same source: non-UI covers line/function A and MacUI covers line/function B. Neither partition alone is fully covered.
- **Expected output**: One LCOV at `coverage/lcov.info` reports both A and B covered, matching the real LLVM union; thresholds remain unchanged.
- **Observable side effect**: Readable merged report; neither saved partition profile was overwritten by the second test run.
- **Assertion strategy**: Level 2 — read report records and totals and compare with the known complementary profile union. Use real LLVM merge/export for a tiny compiled fixture where practical; executable stubs may supplement failure cases.
- **Mock boundary**: None for the tiny real LLVM fixture; if external LLVM fixtures are used, they must reject missing input contributions rather than returning canned success.
- **Paired integration test**: Real split package and LLVM coverage acceptance.
- **Refactor that would break this**: Changing public report path, exclusion contract, or losing one partition’s contribution.

### Case: Re-export is stable and a new run cannot inherit old coverage
- **Category**: state
- **Lane**: integration
- **Spec level**: S5 — idempotence and replacement across run transitions.
- **Input**: Successful run A covers source markers A and B; export twice. Run B covers only marker C; export again.
- **Expected output**: Run A’s two exports have identical covered identities and totals; run B reports only current-run coverage and cannot retain A/B hits.
- **Observable side effect**: Current LCOV replaces earlier LCOV.
- **Assertion strategy**: Level 2 — compare parsed coverage identities/counts rather than timestamps or incidental record order.
- **Mock boundary**: External Swift/LLVM executables only when necessary.
- **Paired integration test**: Real split package and LLVM coverage acceptance.
- **Refactor that would break this**: Accumulating profiles across attempts or changing documented output semantics.

### Case: Missing, stale, malformed or partial coverage fails closed
- **Category**: guard
- **Lane**: integration
- **Spec level**: S3 — classes of invalid coverage evidence.
- **Input**: Table of missing non-UI profile, missing MacUI profile, zero-byte profile, mismatched run identity, absent/incomplete success evidence, malformed profile, and previous LCOV with both current profiles absent.
- **Expected output**: Every case exits nonzero and explains why a trustworthy merged report cannot be produced.
- **Observable side effect**: Existing LCOV cannot be presented as a newly successful report.
- **Assertion strategy**: Level 1/2 — assert failure, useful error text, and absence of usable success output; invoke actual exporter against real tmpdir states.
- **Mock boundary**: LLVM boundary only for deterministic malformed/export-failure cases.
- **Paired integration test**: Real split package and LLVM coverage acceptance.
- **Refactor that would break this**: Weakening freshness/completeness guards; internal storage layout should remain encapsulated by fixture helpers.

### Case: LLVM export failure cannot leave a successful partial LCOV
- **Category**: failure
- **Lane**: integration
- **Spec level**: S3 — interrupted report generation.
- **Input**: Valid current-run profiles; LLVM executable emits half a report and exits 1. Seed a previous successful LCOV first.
- **Expected output**: Export exits nonzero; no partial/current report qualifies as success.
- **Observable side effect**: Consumer cannot read a successful current report from either stale or partial output.
- **Assertion strategy**: Level 1/2 — assert status and verify consumer rejection.
- **Mock boundary**: External LLVM executable.
- **Paired integration test**: Real split package and LLVM coverage acceptance.
- **Refactor that would break this**: Losing atomic/fail-closed publication semantics.

### Case: Real split package and LLVM coverage acceptance
- **Category**: success
- **Lane**: integration
- **Spec level**: S5 — both real partitions contribute to the final evidence.
- **Input**: Actual package at the named baseline or implementation SHA, mandatory shared heavy lock, production runner deadline, real Swift and LLVM.
- **Expected output**: Both CI-equivalent partitions complete, their counts sum to the total suite count, runner exits 0, and the merged LCOV passes configured thresholds without changing exclusions.
- **Observable side effect**: Retained logs, profiles and merged LCOV.
- **Assertion strategy**: Level 3 — check real completed summaries, exit statuses and the actual guardian coverage result; compare repeated before/after outcomes.
- **Mock boundary**: None — real implementation.
- **Refactor that would break this**: A public CLI/configuration/report contract change or actual regression; internal structure does not matter.

## Unit: Unit-lane configuration

**Law**: No independent law: this is a static public command/deadline contract.

### Case: Configured unit execution uses the shared bounded path
- **Category**: success
- **Lane**: contract
- **Spec level**: S2 — boundary between lock wait, execution deadline and outer timeout.
- **Input**: Repository guardian config and runner’s documented maximum timing budget.
- **Expected output**: Unit command invokes the shared runner; coverage command invokes the merged exporter; the outer timeout exceeds the permitted lock wait plus bounded execution/cleanup; thresholds equal lines 100/functions 100/branches 0/statements 100.
- **Observable side effect**: None.
- **Assertion strategy**: Level 1 — parse config and compare public command/timeout/threshold values. Pair this static contract check with actual runner execution rather than treating command-string assertions as behavior coverage.
- **Mock boundary**: None — real configuration.
- **Refactor that would break this**: A deliberate change to public lane commands or timing policy.

# Test Matrix — WI-2: Shared bounded runner in owner gates

## Unit: `owner-gates.sh`

**Law**: Every completed invocation has one truthful status per lane and a final `DONE`; a failed Swift/coverage transition cannot become a passing status through previous run artifacts.

### Case: Successful owner summary accounts for both Swift partitions
- **Category**: success
- **Lane**: integration
- **Spec level**: S5 — summary conserves the two partition counts.
- **Input**: Temporary Git worktree with real owner-gates script; executable tool fixtures yield non-UI 3 tests and MacUI 2 tests, full current coverage, and successful remaining gates.
- **Expected output**: Exit 0; correct head; `swift=0`, `lcov=0`; both partition counts and total 5; remaining lane statuses; one final `DONE`.
- **Observable side effect**: Summary and logs contain the same evidence.
- **Assertion strategy**: Level 1/2 — execute real shell script and read summary/logs; assert total equals partition sum, rather than accepting the final partition as the full suite.
- **Mock boundary**: External Swift, LLVM, Xcode and design tools, preventing heavyweight launches from Node regression tests.
- **Paired integration test**: Real owner Swift/coverage path acceptance below; unrelated build/design tools retain existing coverage and are outside the changed behavior.
- **Refactor that would break this**: Changing public summary protocol or reporting incorrect results.

### Case: Swift failure or timeout remains failed despite stale coverage
- **Category**: state
- **Lane**: integration
- **Spec level**: S5 — earlier success is revoked on the next failed invocation.
- **Input**: Successful owner run, then same output locations with runner exit 1 or 124; retain seeded prior LCOV; later lane fixtures succeed.
- **Expected output**: Overall exit 1; nonzero `swift` and `lcov`; remaining lane statuses and final `DONE`; no successful aggregate Swift claim.
- **Observable side effect**: New summary replaces earlier passing summary; logs name failure/timeout.
- **Assertion strategy**: Level 1/2 — assert statuses, report rejection, later-lane completion and summary content.
- **Mock boundary**: External heavy executables only.
- **Paired integration test**: Real owner Swift/coverage path acceptance; actual runner timeout integration case.
- **Refactor that would break this**: Hiding an earlier lane failure, reusing stale coverage, or aborting before ordinary later lanes.

### Case: Coverage export failure remains visible while later lanes complete
- **Category**: failure
- **Lane**: integration
- **Spec level**: S3 — successful tests with failed reporting.
- **Input**: Swift partitions complete; LLVM exporter fails; remaining tool fixtures succeed.
- **Expected output**: Overall exit 1; `swift=0`, nonzero `lcov`; later statuses and `DONE`.
- **Observable side effect**: Coverage log explains export failure.
- **Assertion strategy**: Level 1/2 — assert truthful summary values and retained error evidence.
- **Mock boundary**: External tool executables.
- **Paired integration test**: Real owner Swift/coverage path acceptance.
- **Refactor that would break this**: Collapsing independent Swift/coverage statuses or losing later-lane continuation.

### Case: Invalid head and unwritable summary fail closed
- **Category**: guard
- **Lane**: integration
- **Spec level**: S2 — invocation precondition boundaries.
- **Input**: Temporary worktree with mismatched requested SHA; separately use a summary destination obstructed by a regular file.
- **Expected output**: Head mismatch exits 2; summary-write failure exits nonzero with a clear message; neither emits a passing `DONE` summary or launches heavy tools.
- **Observable side effect**: No misleading successful summary.
- **Assertion strategy**: Level 1/2 — assert exits and output, confirm absence of fixture launch markers.
- **Mock boundary**: External tools solely as launch sentinels; real Git/filesystem.
- **Paired integration test**: Real owner Swift/coverage path acceptance.
- **Refactor that would break this**: Weakening invocation/write-error guards; formatting unrelated diagnostics need not.

### Case: Real owner Swift/coverage path acceptance
- **Category**: success
- **Lane**: integration
- **Spec level**: S5 — owner and guardian paths agree on current-run evidence.
- **Input**: Run the actual shared runner and merged exporter through owner-gate invocation at the implementation SHA under the mandatory lock.
- **Expected output**: Correct current head, both real partition counts and their total, truthful Swift/LCOV statuses, and retained logs. Full owner invocation preserves all other lane statuses and `DONE`.
- **Observable side effect**: Owner summary and real merged coverage.
- **Assertion strategy**: Level 3 — inspect actual owner output and coverage totals against guardian-run results.
- **Mock boundary**: None — real changed execution path.
- **Refactor that would break this**: Public owner summary or execution-contract change; internal refactoring is tolerated.
