# Test Matrix — WI-1: Bound the unchanged full parallel local unit run

Plan: `.claude/tdd-guardian/plan-20261110-i632-bound.md`.

Use Node's test runner, actual temporary files, actual child processes and the existing watchdog. External executable fixtures are the only mocked boundary. No CI, product, exporter or threshold changes. Production CLI keeps fixed budgets; tests shorten budgets only through the exported launcher function.

## Unit: `scripts/tdd/unit-lane.mjs`

**Law**: The run starts after lock admission, executes once, preserves ordinary command results, and retains separate evidence for every invocation. A timeout ends owned processes rather than silently succeeding or retrying.

### Case: Normal success and test failure retain output/status without retry
- **Category**: success
- **Lane**: integration
- **Spec level**: S2 — success and ordinary nonzero-status partitions.
- **Input**: External Swift fixtures emit recognizable stdout/stderr, a completed full-suite summary, and exit 0 or 1. They record launch count and reject arguments differing from `test --package-path Packages/MadoKit --enable-code-coverage`.
- **Expected output**: Launcher preserves each status and output; exactly one Swift attempt; no partition/filter/serial flags.
- **Observable side effect**: One retained log per invocation; attempt record shows no retry.
- **Assertion strategy**: Level 1/2 — execute actual launcher and watchdog, assert status/output and read attempt/log files. Exact argument checks supplement observable success/failure rather than standing alone.
- **Mock boundary**: External Swift executable only; actual launcher, watchdog, filesystem and subprocess operations.
- **Paired integration test**: Actual full parallel Swift and unchanged LLVM coverage acceptance.
- **Refactor that would break this**: Changing public command/result behavior; internal renaming does not.

### Case: Hung Swift with detached helper times out and releases owned processes
- **Category**: failure
- **Lane**: integration
- **Spec level**: S3 — recurrence of lock-holding hang, including Swift's separate helper group.
- **Input**: Short exported-function test budget; external Swift fixture starts a TERM-resistant helper in another process group, records both PIDs and hangs. The real existing watchdog performs capture and cleanup.
- **Expected output**: Exit 124; explicit deadline/timeout message; no retry; completion within short execution budget plus configured diagnostic/cleanup allowance and generous scheduling margin.
- **Observable side effect**: Retained `run-*` test log and diagnostic directory; recorded leader/helper PIDs are no longer alive; an independent follower can acquire the isolated test lock after the launcher exits.
- **Assertion strategy**: Level 3/2 — run real processes and lock, measure upper bound, assert actual PID liveness, follower admission and retained diagnostic files. Do not mock watchdog internals or process-kill functions.
- **Mock boundary**: External Swift command only; actual OS process and lock operations.
- **Paired integration test**: Existing `test-watchdog.test.mjs` detached-helper/orphan-helper cleanup cases, plus Actual full parallel Swift and unchanged LLVM coverage acceptance for real Swift success.
- **Refactor that would break this**: Losing timeout status, evidence retention or owned-worker cleanup; internal decomposition remains free.

### Case: Queue delay consumes none of the Swift execution budget
- **Category**: boundary
- **Lane**: integration
- **Spec level**: S5 — admission precedes execution-budget start.
- **Input**: Hold a unique real test lock longer than the shortened exported-function Swift budget; queue launcher; release holder; Swift fixture completes within its own budget after admission.
- **Expected output**: Exit 0 despite elapsed queue time exceeding Swift budget; Swift starts only after holder releases the lock.
- **Observable side effect**: Real admission/start timestamps prove ordering; completed retained log.
- **Assertion strategy**: Level 3 — assert actual timestamps/status and that the lock holder remains untouched while launcher queues. Use isolated lock state and normal lock code, never bypass another job's production lock.
- **Mock boundary**: External Swift command only.
- **Paired integration test**: Actual full parallel Swift and unchanged LLVM coverage acceptance uses the mandatory shared lock and 7200-second acquisition allowance.
- **Refactor that would break this**: Starting watchdog outside the lock or incorrectly expiring queue wait at the Swift deadline.

### Case: Consecutive invocations never overwrite earlier evidence
- **Category**: state
- **Lane**: integration
- **Spec level**: S5 — evidence identities remain distinct across run transitions.
- **Input**: Invoke launcher twice against the same capture root without cleanup; first log includes `first-run` and second includes `second-run`. Retain a first-run diagnostic marker before the second attempt.
- **Expected output**: Two different filesystem-created `run-*` directories with correct independent logs; first log/diagnostic remains byte-for-byte intact.
- **Observable side effect**: Both directory trees persist under `.build/unit-watchdog` or an isolated equivalent supplied to the exported function.
- **Assertion strategy**: Level 2 — compare distinct paths and saved bytes before/after the second invocation. Do not assert a timestamp-based name format beyond public `run-*` convention.
- **Mock boundary**: External Swift executable only.
- **Paired integration test**: Actual full parallel Swift and unchanged LLVM coverage acceptance checks persistent real run path.
- **Refactor that would break this**: Reusing/deleting a previous capture directory; internal naming algorithms can change while uniqueness holds.

## Unit: Owner Swift/coverage gate integration

**Law**: A failed current Swift attempt cannot obtain a passing coverage status from prior artifacts. Completed summaries retain truthful lane results and final DONE even after an ordinary Swift failure.

### Case: Owner records timeout/failure and rejects stale coverage while finishing later lanes
- **Category**: state
- **Lane**: integration
- **Spec level**: S5 — current failure revokes previous successful coverage evidence.
- **Input**: Seed old passing `coverage/lcov.info` and Swift profile; then execute actual owner-gates shell with external Swift fixture exiting 1, or hanging until real shared launcher returns 124. Later external tool fixtures succeed. Exporter launch is observed using a system-tool marker rather than mocking repository functions.
- **Expected output**: Overall owner exit 1; summary `swift=1` or `swift=124`; nonzero `lcov`; explicit skipped-coverage reason; no coverage-export invocation; later lane statuses and one final DONE.
- **Observable side effect**: New summary/logs truthfully record current failure; stale LCOV is not counted as a passing current report.
- **Assertion strategy**: Level 1/2 — execute real owner script and actual shared launcher, read summary/logs and confirm absence of coverage-tool launch markers. Timeout fixture may use shortened exported test budgets through the test harness, keeping production CLI fixed.
- **Mock boundary**: External Swift/Xcode/npm/other heavyweight tool executables only. Use actual owner script, launcher and watchdog for the changed path.
- **Paired integration test**: Actual full parallel Swift and unchanged LLVM coverage acceptance; existing watchdog cleanup cases pair timeout mechanics. Unchanged unrelated build/design tools are outside this change.
- **Refactor that would break this**: Treating stale coverage as current, losing 124 in the summary, or stopping before later ordinary lanes/DONE.

### Case: Owner normal success preserves full-suite summary and coverage checking
- **Category**: success
- **Lane**: integration
- **Spec level**: S2 — valid coverage and below-threshold coverage outcomes.
- **Input**: Successful full-suite Swift fixture reports 7 tests; unchanged exporter external-tool fixtures yield either 2/2 lines and functions or 1/2; later lane fixtures pass.
- **Expected output**: `swift=0` and full-suite 7-test summary retained; 2/2 gives `lcov=0` and overall pass; 1/2 gives failing LCOV and overall failure; both complete later statuses and DONE.
- **Observable side effect**: Coverage totals and actual exporter output appear in retained owner logs.
- **Assertion strategy**: Level 1/2 — run actual shell, unchanged exporter and real coverage-total checker; assert totals and status change for reduced coverage.
- **Mock boundary**: External Swift/LLVM/Xcode/npm executables only; actual repository exporter/checker.
- **Paired integration test**: Actual full parallel Swift and unchanged LLVM coverage acceptance.
- **Refactor that would break this**: Changing full-suite result protocol, skipping coverage after success, or weakening thresholds.
