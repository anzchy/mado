## Unit: AppTests all-roots foreground completion barrier

**Law**: A foreground waiter succeeds only after every expected root's readiness event, independent of waiter/producer scheduling; each phase consumes its own observations exactly once. Cancellation terminates a pending wait exactly once and removes its observer. The next MainActor phase starts after the final callback's current actor job has finished clearing recheck.

### Case: Held B blocks the second move despite A cache publication
- **Category**: state
- **Lane**: integration
- **Spec level**: S5 — preserves ordering across arm → foreground1 → A ready → B held → B ready → second move → foreground2.
- **Input**: Fully started fixture with exactly saved roots A and B, active window on B, A moved container/album → staging. Register barrier before foreground1; hold B's actual enumeration after A has completed. A remains readable at staging.
- **Expected output**: At the positive B-held synchronization point A cache is staging, barrier is positively known registered/pending with observed IDs exactly {A}, completion and second-move flags are false, and the container has not replaced staging. A false scheduling flag alone is not proof. After releasing B, phase1 returns, then the real second move occurs and foreground2 completes a new all-roots pass with A cache at container. No direct probe substitutes for either pass.
- **Observable side effect**: Real temporary-directory locations, FileAccess cached root URLs, readiness events and foreground progression.
- **Assertion strategy**: Level 4 — synchronously inspect positively registered/pending waiter state and observed-root set exactly {A}, plus completion/phase flags on MainActor at the known B-held barrier; assert expected cache and filesystem locations before release and exact container path after the second foreground completion. The negative check is supported by the barrier's outstanding B dependency and controlled suspension, not an elapsed delay or a task that may not have started.
- **Mock boundary**: Existing mount/bookmark OS adapters; extend only test-owned mount gate to identify the actual B hold. Real AccessMonitor, NotificationCenter, FileAccess and filesystem remain active.
- **Paired integration test**: accessSystemAdapterCreatesAndResolvesRealBookmark, issue140SystemFileBookmarkFollowsSameVolumeRename and issue73SystemScopeReadabilityReflectsRealFiles exercise real configured system adapters. Real filesystem/notification behavior is exercised here; physical mounts and actual TCC remain NOT VERIFIED.
- **Refactor that would break this**: Premature phase completion before all roots, missing second real foreground recheck or changed actor completion ordering. Internal renames alone should not affect the contract.

### Case: Cancel while B is held terminates the waiter and cleans up
- **Category**: failure
- **Lane**: integration
- **Spec level**: S5 — pending → cancelled transition terminates once without requiring the missing readiness event; cancellation/registration and completion competition preserve exactly-once termination.
- **Input**: Same exact readable A/B fixture, no own foreground recheck active in setup. Start real foreground1 through the barrier, positively establish its registered pending state with observed IDs {A} and B's enumeration held, then cancel the waiting task before releasing B. Also force cancellation before registration to cover that registration race; the cancellation path must not strand a continuation if its handler runs first.
- **Expected output**: Waiting task promptly exits with CancellationError while B is still held. Its readiness observer is removed and waiter terminal state is cancelled exactly once. Then release B and await a positive marker from the continuing real pass or gate cleanup, confirming late readiness cannot resume the cancelled waiter. No sleep or real-time timeout is the test mechanism.
- **Observable side effect**: Thrown CancellationError, removed observer registration/terminal waiter state, and drained held mount enumeration.
- **Assertion strategy**: Level 4 — await and catch CancellationError from the cancelled task; inspect test-owned observer-registration state and terminal result, then explicitly release held B and await a positive drain/completion event. No production observer-inspection seam is allowed; test-owned lifetime state or equivalent existing observable is sufficient. In a completion/cancel race, allow success only if both readiness IDs were already received, otherwise require cancellation; never double resume.
- **Mock boundary**: Existing mount/bookmark OS adapters only, with the same real monitor as the success case. Test-owned gate and waiter state are real, not mocked return values.
- **Paired integration test**: Held B blocks the second move despite A cache publication, and named system-adapter cases above.
- **Refactor that would break this**: Bare checked-continuation wait ignoring cancellation, registering an observer after cancellation without removing it, or late readiness resuming an already-cancelled waiter.

## Completion-proof analysis required before implementation

- Fixture initialization grants only A and B (LostAccessRecoveryTests.swift:193). Assert this exact saved-ID set at the phase setup point to make the finite barrier assumption explicit.
- AccessMonitor.recheckRoots serially loops saved records; readiness callbacks are synchronous MainActor calls after each readable root's reportReadFailure completes (AccessMonitor.swift:412–429).
- After the final expected callback there is no further await before loop return and requestRecheck's recheck=nil (lines 407–409). A continuation resumed there must reenter MainActor after the current actor job; the next phase therefore cannot post while that pass remains marked active. If the actual implementation of the helper adds another task hop, cached observation or production suspension that defeats this argument, stop and redesign using existing observables; do not silently claim the proof.
- Complete monitor startup before arming the forced mount gate; ensure no own foreground recheck is active at phase setup or drain an initial full pass before installing the phase observer. Exactly saved A/B must complete in the same pass, never a mixture of separate passes. An arbitrary existing pass or startup enumeration must not be mislabeled as the forced B operation.
- Failure paths outside the readable two-root fixture are not new production requirements. Unexpected lost root leaves the positive barrier unsatisfied; required cancellation handling must let the original trait cancel the waiter and finish rather than hanging forever on a checked continuation.
