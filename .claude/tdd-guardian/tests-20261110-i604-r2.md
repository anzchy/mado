## Unit: CanvasWindowController sidebar presentation/load path (WI-1)

**Law**: Root reachability after main-read failure depends on the current read state, not on whether the independent sidebar listing/count happened to fail first or succeed first. Newest navigation owns all presented tree state.

### Case: issue604ScanOnlyFailureKeepsRootDespiteSuccessfulSidebarLoad
- **Category**: failure / state
- **Lane**: integration (headless App bundle `app-red`; no showWindow/orderFront or GUI interaction).
- **Spec level**: S5 — sidebar success → main scan failure → held Retry reading → repeated failure retains readable-root reachability.
- **Input**: Real Parent/{Locked,Readable}, with distinct PNG counts. Open Parent to completion. Open Locked while its real sidebar listing and count complete successfully; hold only the main folder scanner after a partial batch. Confirm Locked's sidebar load has completed, then release main scan with a read error while Parent remains readable. Trigger Retry and hold its main scan before completion, then fail it again.
- **Expected output**: Once main scan fails, Parent is at L0, Locked is the uniquely selected row at L1, Readable is an actionable sibling at L1. Locked shows visible `—`, never the successfully counted or partial main-scan count. Parent and Readable do not show failure dash. During held Retry, Parent and Readable remain reachable and Locked shows no numeric count; repeated failure restores its visible dash without losing root/siblings. Successful normal child browsing before failure still uses the existing parent/current/children projection; this case adds siblings only when the main read fails or retries that failure.
- **Observable side effect**: Visible AppKit row URLs/depth/current flags/count labels and read-failure/reading presentation, observed at explicit scanner gates.
- **Assertion strategy**: Level 4 — assert successful sidebar-load completion before releasing scan failure, then exact Parent/Locked/Readable topology and unique selection after failure and during held Retry; Level 1 — assert dash after failure, absence of numeric count during Retry, and unaffected sibling counts. These assertions must fail an implementation that only recovers the root when sidebar enumeration throws.
- **Mock boundary**: Deterministic main filesystem scan failure/completion gate only; sidebar uses real SystemSidebarFolderEnumerator and FileAccess against temporary directories. Do not inject a sidebar listing/count failure for this case.
- **Paired integration test**: `issue604ReadableChildRetainsExistingProjection` covers the complete successful App read path, and `sidebarListingCountsRealDirectImagesAndKeepsLease` covers real enumeration/counting/boundaries.
- **Refactor that would break this**: Installing failure-root topology solely in the sidebar enumeration catch path; allowing a successful sidebar count to overwrite the main-read failure dash; clearing recovery siblings at Retry start.
