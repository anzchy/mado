# Plan — #507 fix round 3: a cold drop of a folder link reaches the folder panel

Source: `~/.picsee/herdr/opus-imple-1/i507-fix3-brief.md`. Device run smoke507-20261107 (signed 10ee8fae): Finder drop of
`link -> real`, never opened before, shows "None of These Files Can Be Opened". Owner decision 2026-11-07,
「Same as a plain folder (Recommended)」.

## Diagnosis (sandboxed probe, 2026-11-07)
A probe app signed with only `com.apple.security.app-sandbox` was run on `~/Documents/x/link -> real` and
`flink -> real/a.png`, neither granted:
- `isReadableFile(link)` = false, `startAccessingSecurityScopedResource()` = false, listing denied;
- `fileExists(atPath:isDirectory:)` = true with dir=true for `link` and dir=false for `flink`;
- `resolvingSymlinksInPath()` gives the target path.
So the sandbox allows metadata reads and denies data reads. Fix2's `deliveredFolder` returns nil when the selection is
neither readable nor startable, *before* it reads the metadata. That is the device failure. A file link can be
told apart from a folder link by the same metadata.

## WI-1: deliveredFolder classifies on metadata alone and never starts a scope
- Remove the readable/start guard and the scope. Classify on `fileExists(isDirectory:)` (follows links) and
  return the canonical target as a directory URL. A file link, a file, a dangling link or a non-file URL → nil.
  Those keep the old classification, unchanged.
- A metadata read needs no scope (#233: FileAccess scopes only what it reads), so the method starts none.
- AC: a folder link (raw, no trailing slash) and an unhinted plain folder → canonical target, for every
  readable × startable combination; a file link → nil in the same combinations; the method starts no scopes;
  no Access Root record or roots file.
- Spec corrections: `issue507UnstartableSelectionNeedsProcessReadability(readable: false)` expected nil. That
  expectation encodes the device failure (unreadable + unstartable = a sandboxed drop of a link), so it changes to
  the canonical target. `issue507UnreadableStartableSelectionTakesItsScopeOnce` expected one scope start; it
  becomes no start.
- Tests: `Packages/PicseeKit/Tests/PicseeInfrastructureTests/Issue507DeliveredFolderClassificationTests.swift`.

## Not changed
App `openInput`, the prompt route, the panel, persistence: they already work once `deliveredFolder` names the
target (Flow 3 PASS on device, App lane covers drop → prompt → grant).

## Risks
- If some location denies even metadata, the link falls back to the old classification. Without the target's
  metadata, a file link and a folder link can't be told apart (readlink gives a path, not a type), so this round
  doesn't guess. Not observed in the probe.
- The probe isn't Picsee; the device smoke confirms.
